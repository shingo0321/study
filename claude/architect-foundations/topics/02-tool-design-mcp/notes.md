# 02. Tool Design & MCP(18%)

## この分野が扱うこと

エージェントがモデルの「手足」として使うツールをどう設計するか、そして複数のクライアント・サーバー間でツールやコンテキストを標準化して共有するプロトコルであるMCP(Model Context Protocol)のアーキテクチャを扱う。「動くツール」ではなく「モデルが正しく・安全に・迷わず使えるツール」を設計する視点が問われる。

## 良いツールインターフェースの設計原則

- **名前は動詞+対象で一意に**: `search_customers` のように、何をするツールかが名前だけで分かるようにする。似た名前・曖昧な名前のツールが並ぶとモデルの選択ミスを誘発する。
- **説明(description)はモデル向けのドキュメント**: いつ使うべきか、いつ使うべきでないか、副作用の有無(読み取り専用か破壊的操作か)を明記する。人間向けのAPIドキュメントよりも「使い所の判断基準」を書くことが重要。
- **スキーマは narrow かつ明示的に**: 自由入力の文字列よりもenum・構造化された引数にする方がモデルの誤用を減らせる。必須/任意パラメータを明確にし、デフォルト値の挙動も説明する。
- **ツールの数と粒度**: ツールが多すぎる・粒度が細かすぎるとモデルの選択負荷が上がり誤選択が増える。逆に1つのツールに機能を詰め込みすぎると引数が複雑化し誤用を招く。「1ツール1責務」を基本に、関連操作は妥当な単位でまとめる。
- **エラーメッセージもモデル向けに設計する**: 単なるスタックトレースではなく、モデルが次にどう行動を修正すべきかが分かる自然文のエラーを返す設計にする(例: 「該当IDが存在しません。search_customersで正しいIDを確認してください」)。
- **冪等性と副作用の明示**: 読み取り専用ツールと状態変更ツールを名前・説明で区別し、エージェントが不用意に再実行しても安全かどうかを設計・文書化する。

## MCPのアーキテクチャ概要

MCPは、モデル(クライアント)が外部のデータソース・ツール・プロンプトに統一的な方法でアクセスするためのオープンプロトコル。**MCPサーバー**が能力を公開し、**MCPクライアント**(Claude Desktop、Claude Code、独自のアプリなど)がそれに接続する、という構成。

### 3つのプリミティブの使い分け

- **Tools(ツール)**: モデルが呼び出せるアクション。副作用を持ちうる(検索、書き込み、外部API呼び出しなど)。モデルが自律的に「いつ呼ぶか」を判断する。
- **Resources(リソース)**: モデルやユーザーが参照できる読み取り専用のデータ(ファイル、DBレコード、ドキュメントなど)。ツールと違い、通常はアプリケーション側やユーザーが明示的に選んでコンテキストに含める性質のもの。
- **Prompts(プロンプト)**: サーバー側が提供する再利用可能なプロンプトテンプレート・ワークフローの雛形。ユーザーが明示的に選択して起動する用途を想定。

アーキテクト視点では「この機能はモデルに自律判断させたい(Tool)のか、明示的にユーザー/アプリが選ぶもの(Resource/Prompt)なのか」を切り分けることが設計の出発点になる。

## トランスポートの選択

- **stdio**: ローカルプロセスとして起動するMCPサーバー向け。ローカルツール・ファイルシステムアクセスなど、クライアントと同じマシン上で完結する用途に適する。プロセス起動のオーバーヘッドはあるが構成がシンプルで、認証もOS権限に委ねられる。
- **HTTP(リモート)ベースのトランスポート**: リモートのMCPサーバーに接続する用途向け。複数クライアントから共有される社内サービスや、SaaS化されたMCPサーバーに適する。ネットワーク越しの認証・認可(OAuth等)や可用性の設計が必要になる。

選択基準: 「サーバーをどれだけの利用者・クライアントで共有するか」「ローカルリソース(ファイル・ローカルDB)へのアクセスが要るか」「認証をどのレイヤーで行うか」で決める。

## 権限・スコープ設計

- **最小権限の原則**: MCPサーバーが公開するツールは、そのユースケースに必要な範囲に絞る。汎用的すぎるツール(任意コマンド実行など)は強力だが誤用・悪用のリスクが大きい。
- **クライアント側の許可制御**: どのツールを自動実行してよいか、どのツールに人間の承認が必要かをクライアント側のポリシーとして設計する(Claude Codeのpermission modeなどが実例)。
- **マルチテナント環境でのスコープ分離**: 1つのMCPサーバーを複数ユーザー・組織で共有する場合、リクエストごとに認可コンテキストを渡し、ユーザーがアクセスできるデータ・操作だけに制限する設計が必須。
- **監査ログ**: 誰が・いつ・どのツールを・どんな引数で呼んだかを記録できる設計にしておくと、事後の検証やインシデント対応がしやすい。

## ツール契約(コントラクト)のバージョニング

- ツールの名前・スキーマは一種のAPI契約であり、エージェントやワークフローがそれに依存する。**破壊的変更(引数の意味変更・必須化・削除)は新しいツール名やバージョン番号を切って提供し、旧クライアントを壊さない**ようにする。
- 説明文(description)の変更もモデルの挙動に影響するため、軽微に見えても実質的には契約変更として扱い、変更後の挙動をテストする。
- サーバー側の機能追加(新しいツール・リソースの追加)は基本的に後方互換だが、クライアント側がツール一覧を静的にキャッシュしている場合は再取得のタイミングを考慮する。

## 押さえておくべきポイント

- 良いツール設計は「名前・説明・スキーマ」の3点でモデルの誤用を防ぐことが核心。説明文には使い所の判断基準を書く
- ツールの粒度は多すぎても少なすぎても選択ミスを招く。「1ツール1責務」が基本方針
- MCPの3プリミティブ(Tools/Resources/Prompts)は「モデルが自律判断するか」「人間・アプリが明示選択するか」で使い分ける
- トランスポート選択(stdio vs リモートHTTP)はローカル完結か複数クライアント共有かで決まる
- 権限設計は最小権限・クライアント側の承認ポリシー・マルチテナント分離・監査ログが柱
- ツールスキーマ・説明文はAPI契約として扱い、破壊的変更はバージョニングして後方互換を守る
