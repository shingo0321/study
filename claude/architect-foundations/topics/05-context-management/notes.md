# 05. Context Management(15%)

## この分野が扱うこと

長時間稼働するエージェントや大規模なドキュメント・コードベースを扱うシステムで、**限られたコンテキストウィンドウをどう配分し、どう再利用し、どう圧縮するか**を扱う。RAGアーキテクチャの設計、プロンプトキャッシュ戦略、要約・圧縮(compaction)、マルチターンの状態管理など、コンテキストを「有限で高コストな資源」として設計する視点が問われる。

## コンテキストウィンドウの予算設計

- コンテキストウィンドウは、システムプロンプト・ツール定義・会話履歴・検索結果・ツール実行結果など複数の要素が競合する有限資源として扱う。**アーキテクトはこれらに「予算」を割り当てる**発想を持つ。
- 予算配分の考え方の例:
  - 固定で毎回必要なもの(システムプロンプト、ツール定義)は極力コンパクトに保つ
  - 可変で大きくなりがちなもの(検索結果、ファイル内容、ツール出力)は上限を設けて切り詰める、または要約してから挿入する
  - 会話履歴は無制限に蓄積させず、古いターンを要約・破棄する方針をあらかじめ決めておく
- **ウィンドウが埋まるほど精度が落ちうる**(関連情報が埋もれる、いわゆるlost-in-the-middle的な問題)ことを踏まえ、「入るかどうか」だけでなく「関連性の高い情報を優先的に、かつ見つけやすい位置に置く」設計が重要。

## プロンプトキャッシュ戦略

- 変化しない・変化頻度の低い大きなコンテキスト(長いシステムプロンプト、固定のツール定義群、大きな参照ドキュメント)を**プレフィックスとして固定し、キャッシュされる位置に置く**ことで、以降のリクエストのレイテンシとコストを削減できる。
- 設計上のポイント:
  - **キャッシュされる部分は先頭に、可変部分(ユーザー入力・都度変わるデータ)は末尾に**置く、という構造がキャッシュ効率を最大化する基本パターン
  - 頻繁に更新される情報をキャッシュ対象の固定プレフィックスに混ぜてしまうと、キャッシュヒット率が下がりメリットが消える
  - エージェントループのように同一の会話が何ターンも継続するケースは、ターンを重ねるごとにキャッシュされる接頭辞が伸びていくため特に効果が大きい
- キャッシュ戦略はコスト・レイテンシの両方に効くため、ドメイン01の「コスト/レイテンシのトレードオフ」と表裏一体で設計する。

## RAG(検索拡張生成)アーキテクチャ

- **すべてをコンテキストに詰め込む(ロングコンテキスト戦略)** と **必要な部分だけを検索して注入する(RAG戦略)** はトレードオフの関係にある。
  - ロングコンテキスト戦略: 実装がシンプルで検索の取りこぼしリスクがないが、コスト・レイテンシが増え、無関係な情報がノイズになりうる
  - RAG戦略: コンテキストを小さく保てるが、検索の精度(何を取得するか)がボトルネックになり、検索漏れが致命的な欠落を生みうる
- **チャンキング設計**: ドキュメントをどう分割するかが検索精度を左右する。意味的にまとまった単位(セクション単位など)で分割し、チャンクが小さすぎて文脈を失わないようにする。
- **検索対象の設計**: ベクトル検索だけでなく、キーワード検索・メタデータフィルタ・ハイブリッド検索を組み合わせることで精度を上げられる。
- **エージェント統合**: RAGを固定パイプラインとして組むのではなく、「検索ツール」としてエージェントに持たせ、モデル自身に必要な検索クエリを組み立てさせる設計(agentic RAG)は、曖昧なユーザー質問に対して反復的に検索精度を上げられる利点がある。

## 要約・圧縮(compaction)戦略

- 長時間稼働するエージェントや長い会話では、会話履歴がコンテキストウィンドウの上限に近づく前に**古いターンやツール結果を要約して圧縮する**仕組みが必要になる。
- 圧縮の設計選択肢:
  - 古いツール実行結果(大きなファイル内容やAPIレスポンス全体)を、要点だけの要約に置き換える
  - 一定ターン数より前の会話を要約1つにまとめ、詳細を破棄する
  - 重要な決定事項・状態(タスクの進捗、確定した設計判断)は要約時にも失われないよう、構造化されたメモ・外部状態(ドメイン01参照)として別途保持する
- **圧縮のタイミング**: ウィンドウが実際に埋まってから圧縮するのか、余裕があるうちに先回りして圧縮するのかは、レイテンシと情報欠落リスクのトレードオフになる。

## マルチターン状態管理

- 複数ターン・複数セッションにまたがるエージェントでは、**「会話履歴そのもの」と「タスクの状態」を分離して管理する**設計が有効。会話履歴は圧縮・破棄されうるが、タスクの状態(進捗、決定事項、未解決の課題)は独立して永続化する。
- **セッションをまたぐ継続**: ユーザーが後から会話を再開する場合、全履歴を再送するのではなく、要約されたセッションサマリーや外部に保存した状態を初期コンテキストとして再構築する設計にすると、コストと再現性のバランスが取れる。
- **並行セッション・マルチユーザー**: 複数ユーザー・複数セッションが同じバックエンド(ツール・データ)を共有する場合、コンテキスト(会話状態)はセッションごとに厳密に分離し、混線を防ぐ設計が必須。

## 押さえておくべきポイント

- コンテキストウィンドウは複数要素が競合する有限資源であり、固定部分は小さく・可変部分は上限を決めて予算配分する
- プロンプトキャッシュは「固定部分を先頭に、可変部分を末尾に」置く構造で効果を最大化し、コスト・レイテンシ双方に効く
- ロングコンテキストとRAGはトレードオフであり、検索精度(チャンキング・ハイブリッド検索)がRAGの成否を左右する
- 長時間エージェントには要約・圧縮(compaction)戦略が必須で、重要な状態は要約で失われないよう構造化して外部保持する
- マルチターン・マルチセッションでは「会話履歴」と「タスク状態」を分離管理し、セッション間・ユーザー間の混線を防ぐ
