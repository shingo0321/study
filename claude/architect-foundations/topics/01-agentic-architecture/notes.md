# 01. Agentic Architecture & Orchestration(27% — 最重要ドメイン)

> **出典**: 公式の試験ガイド(Claude Certified Architect – Foundations、バージョン1.0、2026年7月施行)のタスク記述1.1〜1.7に沿ってまとめたもの。内容は自分の言葉での要約で、試験問題そのものではない。

## この分野が扱うこと

Claude Agent SDKなどでエージェントを作るときの設計判断を問う。ループの回し方、コーディネーターとサブエージェントの分業、強制すべきルールの置き場所(フックかプロンプトか)、タスクの分解、セッションの再開と分岐が柱になる。配点が最も大きく、カスタマーサポート、マルチエージェント調査、開発者生産性のシナリオで繰り返し出る。

## 1.1 エージェントループの設計

- **ループの流れ**: リクエスト送信 → 応答の`stop_reason`を確認 → ツール実行 → 結果を会話履歴に追加 → 再送、の繰り返し。
  - `stop_reason`が`"tool_use"`なら、要求されたツールを実行して結果を返し、ループを続ける。
  - `"end_turn"`なら、モデルが最終応答を出したので終了する。
- **ツール結果は会話履歴に追加する**。モデルはそれを見て次の行動を決める。
- **モデル主導 vs 事前定義**: 次にどのツールを呼ぶかをモデルが文脈から判断するのがエージェント。決まった順序のツール列や決定木をコードで固定するのは、ワークフローに近い。
- **アンチパターン(出題されやすい)**:
  - 自然言語の応答文を解析して終了を判定する
  - 反復回数の上限を、主な停止条件にする(暴走防止の安全網としては有効だが、主たる終了条件にはしない)
  - アシスタントのテキストがあるかどうかで完了を判定する

## 1.2 コーディネーターとサブエージェントによるマルチエージェント

- **ハブ・アンド・スポーク型**: コーディネーターがすべてのサブエージェント間の通信、エラー処理、情報の経路を管理する。サブエージェント同士が直接やりとりしない構成が基本。
  - 理由は、観測しやすいこと、エラー処理を一貫させられること、情報の流れを制御できること。
- **サブエージェントのコンテキストは隔離されている**。コーディネーターの会話履歴を自動では引き継がない。
- **コーディネーターの役割**: タスクの分解、委譲、結果の統合、依頼の複雑さに応じて呼び出すサブエージェントを選ぶこと。
  - 毎回すべてのパイプラインを通すのではなく、必要なサブエージェントだけを動的に選ぶ。
- **分解が狭すぎるリスク**: コーディネーターがタスクを狭く切りすぎると、広いテーマの調査で抜けが出る。
- **調査範囲の分割**: サブトピックや情報源の種類ごとにサブエージェントへ割り当て、重複を減らす。
- **反復的な改善ループ**: 統合結果の抜けをコーディネーターが評価し、絞った質問で検索・分析をやり直させ、十分になるまで統合を繰り返す。

## 1.3 サブエージェントの呼び出し、コンテキストの受け渡し、起動

- **起動の仕組み**: SDKではTaskツールでサブエージェントを起動する。コーディネーターが使えるように、`allowedTools`に`"Task"`を含める必要がある。
- **コンテキストはプロンプトに明示的に入れる**。サブエージェントは親のコンテキストを自動では引き継がず、呼び出し間でメモリも共有しない。
  - 先行エージェントの調査結果(検索結果、文書の分析結果)は、後続のサブエージェントのプロンプトに丸ごと含める。
- **構造化して受け渡す**: 内容と、メタデータ(URL、文書名、ページ番号)を分けた構造化データで渡すと、出典情報を保てる。
- **AgentDefinition**: サブエージェントの種類ごとに、説明、システムプロンプト、ツール制限を設定する。
- **並列起動**: 1回のコーディネーター応答の中で、複数のTask呼び出しを出す。ターンをまたぐと並列にならない。
- **フォークによる分岐**: 共通の分析結果を土台に、別々のアプローチを試すときに使う(1.7参照)。
- **コーディネーターのプロンプト**: 手順を細かく指示するより、調査の目的と品質基準を示す方が、サブエージェントの適応力を活かせる。

## 1.4 強制と引き継ぎを含む複数ステップのワークフロー

- **強制の方法は2種類**: フックや前提条件のゲートによる**プログラム上の強制**と、プロンプトによる**指示**。
- **決定的な遵守が必要なとき**(例: 返金などの金銭操作の前の本人確認)は、プロンプトだけに頼らない。プロンプトの指示には、ゼロではない失敗率がある。
  - 例: `get_customer`が本人確認済みの顧客IDを返すまで、`process_refund`の呼び出しをプログラムでブロックする。
- **複数の用件を含む依頼**: 用件を個別の項目に分け、共有コンテキストを使って並列に調査し、最後に1つの解決案へ統合する。
- **人間へのエスカレーションの引き継ぎ**: 人間の担当者は会話の記録を見られない前提で、構造化したサマリーを渡す。
  - 顧客ID、根本原因、返金額、推奨する対応などを含める。

## 1.5 Agent SDKフック:ツール呼び出しの横取りとデータの正規化

- **`PostToolUse`系のフック**: ツールの結果をモデルが処理する前に変換できる。
  - 例: MCPツールごとに形式が違う日時(Unixタイムスタンプ、ISO 8601)やステータスコード(数値)を、統一形式に正規化する。
- **ツール呼び出しを横取りするフック**: 実行前に呼び出しを検査し、ルール違反をブロックする。
  - 例: 500ドルを超える返金をブロックして、人間へのエスカレーションに振り向ける。
- **使い分けの原則**: ビジネスルールの遵守を保証したいときは、プロンプトの指示(確率的な遵守)ではなく、フック(決定的な保証)を選ぶ。

## 1.6 複雑なワークフローのタスク分解

- **プロンプトチェイニング(固定の逐次パイプライン)**: 手順が予測できる、多面的なレビューに向く。
  - 例: ファイルごとの個別分析を行い、その後にファイル間の統合パスを実行する。
- **動的で適応的な分解**: 調査の途中で見つかったことに応じて、次のサブタスクを生成する。探索的で終わりの形が決まっていないタスクに向く。
- **大規模なコードレビュー**: ファイルごとの局所的な分析パスと、ファイル間の統合パスに分ける。注意の希薄化を避けられる。
- **オープンエンドなタスクの進め方**(例: レガシーコードにテストを追加する):
  1. 構造を把握する
  2. 影響の大きい領域を特定する
  3. 優先順位をつけた計画を立てる
  4. 依存関係が見つかるたびに計画を調整する

## 1.7 セッション状態、再開、フォーク

- **名前付きセッションの再開**: `--resume <セッション名>`で、特定の過去の会話を続ける。
- **`fork_session`**: 共通の分析結果から、独立した枝を作る。2つのテスト戦略やリファクタリング案を、同じ土台から比べるときに使う。
- **再開時の注意**: 前回の分析後にファイルが変更されていたら、変更されたファイルを具体的に伝えて、再分析を絞り込める。
- **再開か、新規セッション+サマリーか**:
  - 以前の文脈がほぼ有効なら、再開する。
  - ツール結果が古くなっているなら、構造化したサマリーを渡して新しいセッションを始める方が信頼できる。

## 補足:運用上の設計観点

試験ガイドの項目ではないが、シナリオ問題の背景として役立つ観点。

- **human-in-the-loop**: 返金のような不可逆・金銭的影響のある操作にだけ承認ゲートを置き、読み取り中心の操作は自律実行にする(全操作で承認を求めると承認疲れを招く)。
- **長時間タスクの中断対策**: 進捗を外部(ファイルやDB)にチェックポイントとして保存し、再開できるようにする(ドメイン05の5.4参照)。
- **エラー回復**: 一過性エラーは再試行し、恒久的エラーは再試行せずに対処する(ドメイン02の2.2参照)。
- **コストの代償**: マルチエージェントはスループットを上げるが、各サブエージェントが独自のコンテキストを持つため、トークンコストが増えやすい。独立性のあるタスクにだけ使う。

## 押さえておくべきポイント

- ループは`stop_reason`で制御する(`tool_use`なら継続、`end_turn`なら終了)。自然言語の解析や反復回数の上限を主たる終了条件にしない
- サブエージェントのコンテキストは隔離されている。必要な情報はプロンプトに明示的に入れ、出典はメタデータと分けて渡す
- 並列起動は、1回の応答に複数のTask呼び出しを出すこと。コーディネーターの`allowedTools`に`"Task"`が必要
- コーディネーターの分解が狭すぎると抜けが出る。抜けを評価して再委譲する反復ループを設計する
- 金銭操作など決定的な遵守が必要なルールは、フックや前提条件のゲートで強制する。プロンプトは確率的
- 人間への引き継ぎでは、会話記録がない前提で、構造化したサマリーを渡す
- 手順が予測できるならプロンプトチェイニング、探索的なら動的分解。大規模レビューはファイル別+統合パスに分ける
- 再開は文脈が有効なとき、ツール結果が古いならサマリーを渡して新規セッションにする。分岐には`fork_session`
