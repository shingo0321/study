# 03. Claude Code(20%)

## この分野が扱うこと

Claude Code(公式CLIエージェント)そのもののアーキテクチャと、それをチーム・組織のワークフローやCI/CDにどう統合するかを扱う。個人が対話的に使うツールという理解に留まらず、**フックによるガバナンス、サブエージェントの分業、設定・権限モードによる安全性の制御、プロジェクト単位のMCP構成**まで、組織導入を見据えたアーキテクト視点が問われる。

## Claude CodeのCLIアーキテクチャ概要

- ターミナル上で動くエージェント型CLIで、内部的には前述のエージェントループ(モデル↔ツール実行)を回している。ファイル読み書き・コマンド実行・検索など、開発者が普段手で行う操作をツールとして持つ。
- **設定の階層**: ユーザーレベル(グローバル)設定とプロジェクトレベル(リポジトリ内)設定があり、プロジェクト設定はリポジトリにコミットしてチームで共有できる。個人の好み(キーバインド等)はユーザーレベル、チームで統一すべきルール(許可ツール、MCPサーバー構成)はプロジェクトレベルに置くのが基本方針。
- **CLAUDE.md**: プロジェクトのコンテキスト(構造・規約・注意点)をエージェントに与えるための実質的なプロジェクト設定ファイル。ネストされたサブディレクトリごとに置いて、モノレポ内の各サブプロジェクト固有の情報を分離することもできる。

## フック(hooks)によるガバナンス・自動化

- フックは、エージェントのライフサイクルの特定のタイミング(ツール実行前後、応答完了時など)に外部コマンドを実行する仕組み。**モデルの判断に依存せず、決定的に(deterministically)強制したいルール**をフックに実装するのが設計上のポイント。
- 典型的な用途:
  - 危険なコマンド(`rm -rf`等)の実行前ブロック — モデルの判断任せにせず機械的に弾く
  - コミット前のlint/フォーマット自動実行
  - 機密ファイル(`.env`等)への書き込み・読み取りの禁止
  - 監査ログの記録(誰が・いつ・どのツールをどんな引数で実行したか)
- アーキテクト視点: 「モデルにプロンプトで指示する」のと「フックで強制する」のは信頼性が全く異なる。**コンプライアンス上必須の制約はプロンプト任せにせずフックに落とす**のが正しい設計判断。

## サブエージェント設計

- Claude Codeはタスクの一部を専用のサブエージェントに委譲できる。各サブエージェントは独立したコンテキストウィンドウを持ち、特定のツールセット・システムプロンプトを持たせられる。
- 設計判断のポイント(ドメイン01のマルチエージェント議論とも直結):
  - 探索・調査など「大量のコンテキストを消費するが結果は要約でよい」タスクをサブエージェントに切り出すと、メインの会話のコンテキストを汚染しない
  - サブエージェントごとにツールを絞ることで、誤操作のリスクを局所化できる(例: レビュー専用サブエージェントには書き込み権限を与えない)
  - 並列実行可能なサブエージェントはスループットを上げるが、トークンコストは増える

## 設定・権限モード

- Claude Codeは、ツール実行を都度確認するモードから、一定範囲を自動承認するモードまで、**自律性のレベルを段階的に設定できる**権限モデルを持つ。
- アーキテクト視点での設計基準:
  - 読み取り専用操作(検索・閲覧)は自動承認、書き込み・実行系操作は承認を要求、というリスクベースの許可リストが基本
  - 「許可リストに何を載せるか」はプロジェクト設定として明文化し、チームで共有する
  - CI環境など人間が張り付かない実行では、許可範囲を事前に厳密に絞った上で完全自動運用に倒す設計になる(承認待ちで止まるとパイプラインが進まないため)

## プロジェクトレベルのMCP構成

- プロジェクトの設定ファイルにMCPサーバー(社内ツール・DB・チケット管理システムへの接続など)を定義し、リポジトリにコミットすることで、チーム全員が同じ外部ツール群にアクセスできる状態を再現できる。
- 設計上の注意: 認証情報(APIキー等)は設定ファイルに直書きせず環境変数等で注入し、リポジトリには接続設定のみを残す。
- チームで共有するMCPサーバーの構成は、ツール設計(ドメイン02)の原則――最小権限・明確なスコープ――がそのままプロジェクト単位のガバナンスとして適用される。

## CI/CDやチームワークフローへの統合

- **非対話(ヘッドレス)実行**: 人が対話せずに、決まったタスク(コードレビューの一次チェック、定型的なリファクタ、ドキュメント生成など)をパイプラインの一部として自動実行させる使い方。この場合、権限モードは厳格に絞り、フックで逸脱を防止するのが必須設計。
- **PRレビューへの組み込み**: 差分に対する自動レビューコメント生成など、人間レビュアーの一次フィルタとして使う構成。最終判断は人間に残す(human-in-the-loop)ことで責任分界を明確にする。
- **監査・再現性**: チームで使う場合、誰が何を実行させ、どんな変更が生まれたかを追跡できることが重要。フックによるログ記録、Git履歴との紐付けが実務上の設計ポイントになる。
- **ロールアウト戦略**: 個人利用から始めて、フック・許可設定をチーム標準として固め、CLAUDE.mdやプロジェクト設定をリポジトリに定着させてから組織全体に展開する、という段階的な導入が典型的な現実解。

## 押さえておくべきポイント

- 設定はユーザーレベル/プロジェクトレベルで階層化し、チーム共有すべきルールはプロジェクト設定(リポジトリにコミット)に置く
- フックは「モデルの判断に依存させず機械的に強制したいルール」の実装場所。危険操作のブロックや監査ログはフックの典型用途
- サブエージェントはコンテキスト汚染の防止とツール権限の局所化に使う。並列化はスループットとコストのトレードオフ
- 権限モードはリスクベースで段階設計し、CI等の非対話実行では自動承認範囲を事前に厳密化する
- プロジェクト単位のMCP構成は認証情報を分離し、最小権限の原則をチームガバナンスとして適用する
- 組織導入は個人利用→設定の標準化→チーム展開という段階的ロールアウトが現実的
