# 03. Claude Code Configuration & Workflows(20%)

> **出典**: 公式の試験ガイド(Claude Certified Architect – Foundations、バージョン1.0)のタスク記述3.1〜3.6に沿った要約。末尾の「公式ドキュメントに基づく詳細」は、Claude Codeの公式ドキュメントで確認した仕様の補足。

## この分野が扱うこと

Claude Codeをチームの開発ワークフローに組み込むための設定と使い方。CLAUDE.mdの階層、スラッシュコマンドとスキル、パス指定ルール、プランモードと直接実行の使い分け、反復的な改善、CI/CDへの統合が柱になる。コード生成とCIのシナリオで出題される。

## 3.1 CLAUDE.mdの階層、スコープ、モジュール構成

- **3つの階層**:
  - ユーザーレベル: `~/.claude/CLAUDE.md`
  - プロジェクトレベル: `.claude/CLAUDE.md`またはリポジトリ直下の`CLAUDE.md`
  - ディレクトリレベル: サブディレクトリ内の`CLAUDE.md`
- **ユーザーレベルの指示は、その人だけに適用される**。バージョン管理で共有されないので、チームに配りたい規約はプロジェクトレベルに置く。
  - 典型的な診断問題: 新しいメンバーに指示が効かないのは、指示がユーザーレベルにあってプロジェクトレベルにないから。
- **`@import`構文**: 外部のファイルを参照して、CLAUDE.mdをモジュール化する。パッケージごとに、関連する標準だけを取り込める。
- **`.claude/rules/`**: トピック別のルールファイルに分けられる。1つの巨大なCLAUDE.mdの代わりになる(`testing.md`、`api-conventions.md`、`deployment.md`など)。
- **`/memory`コマンド**: どのメモリファイルが読み込まれているかを確認できる。セッションごとに挙動が一貫しないときの診断に使う。

## 3.2 カスタムスラッシュコマンドとスキル

- **コマンドの置き場所**:
  - `.claude/commands/`: プロジェクト用。バージョン管理でチームに共有される
  - `~/.claude/commands/`: 個人用
- **スキル**: `.claude/skills/`に置き、`SKILL.md`のフロントマターで設定する。
  - `context: fork`: 隔離されたサブエージェントのコンテキストで実行する。出力が長くなる処理(コードベース分析)や、探索的な処理(代替案の洗い出し)で、メインの会話を汚さない
  - `allowed-tools`: スキル実行中に使えるツールを制限する(例: 破壊的な操作を防ぐために、ファイル書き込みだけに絞る)
  - `argument-hint`: 引数なしで呼び出されたとき、必要なパラメータを促す
- **個人用のカスタマイズ**: `~/.claude/skills/`に別名の個人版を作れば、チームメイトに影響しない。
- **スキルとCLAUDE.mdの使い分け**: スキルは必要なときに呼び出す、タスク固有のワークフロー。CLAUDE.mdは常時読み込まれる、普遍的な標準。

## 3.3 パス指定ルールによる条件付きの規約読み込み

- **`.claude/rules/`のファイルに、YAMLフロントマターの`paths`**(globパターン)を書くと、一致するファイルを編集するときだけルールが有効になる。
  - 例: `paths: ["terraform/**/*"]`
- **効果**: 無関係なコンテキストとトークン使用が減る。
- **ディレクトリ別のCLAUDE.mdとの違い**: 複数のディレクトリにまたがる規約(コードベース全体に散らばるテストファイルなど)には、globパターンのルールが向く。
  - 例: `**/*.test.tsx`で、置き場所を問わず全テストファイルに適用する。
- 規約が1つのサブディレクトリに収まるなら、そのディレクトリのCLAUDE.mdでよい。散らばるなら、パス指定ルールを選ぶ。

## 3.4 プランモードと直接実行の使い分け

- **プランモードが向くとき**: 大規模な変更、有効な方法が複数ある、アーキテクチャ上の判断、複数ファイルの変更。コードを変更する前に、安全に探索して設計でき、高くつく手戻りを防げる。
  - 例: マイクロサービスの再構成、45以上のファイルに影響するライブラリ移行、インフラ要件の異なる統合方式の選択。
- **直接実行が向くとき**: 範囲が明確で、よく分かっている変更。
  - 例: 明確なスタックトレースがある1ファイルのバグ修正、日付検証の条件を1つ追加する。
- **Exploreサブエージェント**: 長くなる探索の出力を隔離し、要約だけをメインの会話に返す。複数フェーズのタスクでコンテキストの枯渇を防ぐ。
- **組み合わせ**: 調査と計画にプランモード、実装に直接実行(例: ライブラリ移行を計画し、その計画どおりに実行する)。

## 3.5 段階的な改善の反復技法

- **入出力の具体例が最も伝わる**: 文章での説明が一貫せず解釈されるときは、2〜3個の具体的な入出力の例を示す。
- **テスト駆動の反復**: 期待する挙動、エッジケース、性能要件をカバーするテストを先に書き、テストの失敗を共有しながら改善を重ねる。
- **インタビューパターン**: 実装の前に、Claudeに質問させて、開発者が想定していなかった考慮事項を引き出す(キャッシュの無効化方針、障害モードなど。不慣れな領域で有効)。
- **問題の出し方**:
  - 互いに影響し合う問題は、1つの詳細なメッセージでまとめて伝える
  - 独立した問題は、順番に1つずつ直す
- エッジケース(移行スクリプトのnull値など)は、入力例と期待する出力を持つ具体的なテストケースで示す。

## 3.6 CI/CDパイプラインへの統合

- **`-p`(`--print`)フラグ**: 非対話モードで実行する。CIで入力待ちのまま止まるのを防ぐ。
- **構造化出力**: `--output-format json`と`--json-schema`で、機械で解析できる形式の結果を得る。インラインのPRコメントとして自動投稿するときに使う。
- **CLAUDE.mdはCIにもプロジェクトのコンテキストを与える**: テスト標準、フィクスチャの規約、レビュー基準などを書いておく。
  - テスト生成の質が上がり、価値の低い出力が減る。
- **セッションの独立性**: コードを生成したセッションは、自分の変更をレビューするのに向かない。独立したレビュー用インスタンスの方が効果的(ドメイン04の4.6参照)。
- **再レビュー時**: 新しいコミットの後は、前回のレビュー結果をコンテキストに含め、新しい指摘と未対応の指摘だけを報告させる。重複コメントを避けられる。
- **テスト生成**: 既存のテストファイルをコンテキストに含めて、すでにカバーされているシナリオの重複提案を避ける。

## 公式ドキュメントに基づく詳細(2026年10月時点)

出典: Claude Code公式ドキュメントの[フック](https://code.claude.com/docs/en/hooks)・[権限](https://code.claude.com/docs/en/permissions)・[サブエージェント](https://code.claude.com/docs/en/sub-agents)。機能は更新が速いため、最新の仕様は公式ドキュメントで確認すること。

### フックの種類と終了コード

- **イベントは多数ある**: `PreToolUse`(ツール実行前)、`PostToolUse`(成功後)、`UserPromptSubmit`(プロンプト送信時)、`Stop`(応答完了時)、`SubagentStart`/`SubagentStop`、`PreCompact`/`PostCompact`(コンテキスト圧縮の前後)、`SessionStart`/`SessionEnd`、`PermissionRequest`、`ConfigChange` など。
- **設定の構造**は「イベント → マッチャー → ハンドラー」の3階層。マッチャーはツール名で絞り込む(`Bash`、`Edit|Write`、MCPツールは`mcp__<server>__.*`)。
- **ハンドラーの種類**は`command`(シェル実行)、`http`(JSONをPOST)、`mcp_tool`、`prompt`(モデルに単発で判断させる)、`agent`(サブエージェントで検証、実験的)。
- **終了コードの意味**(commandハンドラー):
  - `0`: 成功。stdoutがJSONならそのフィールドが適用される
  - `2`: **ブロッキングエラー**。`PreToolUse`ならツール呼び出しを止め、stderrがClaudeにフィードバックされる
  - その他(`1`を含む): **非ブロッキングエラー**。処理は続行されるので、ブロックしたいときに`exit 1`を使うのは典型的な誤り
- **`PostToolUse`はツール実行後**に動くため、実行を止める用途には使えない(出力の書き換えやClaudeへのフィードバック用)。
- **JSON出力による制御**: `PreToolUse`は`permissionDecision`(`allow`/`deny`/`ask`/`defer`)、`permissionDecisionReason`、`updatedInput`(引数の書き換え)を返せる。終了コードとJSONは1つのフックで併用しない。
- **保存場所**: `~/.claude/settings.json`(個人・全プロジェクト)、`.claude/settings.json`(プロジェクト・コミット可)、`.claude/settings.local.json`(個人・gitignore)、managed policy settings(組織全体)、プラグイン、スキル/サブエージェントのfrontmatter。

### 権限ルールの評価と優先順位

- **ルールは deny → ask → allow の順に評価**され、最初に一致したものが結果を決める。範囲の狭いallowでdenyの例外は作れない(例: `Bash(aws *)`がdenyなら、`Bash(aws s3 ls)`をallowしても拒否される)。
- **スコープをまたいでも同じ**: どのレベルかでdenyされたツールは、他のレベルでallowできない。managed settingsのdenyは、コマンドライン引数(`--allowedTools`)でも覆せない。ユーザー設定のallowもプロジェクト設定のdenyに負ける。
- **managed settings**は組織管理者が配布する最上位の設定で、ユーザー・プロジェクト設定では上書きできない。`permissions.disableBypassPermissionsMode`を`"disable"`にすれば`bypassPermissions`の利用を封じられる。
- **フックと権限ルールの関係**: `PreToolUse`フックの`allow`は、denyルール・askルールを回避しない(denyは拒否、askは確認が出る)。一方、フックが終了コード2で止めた場合は、allowルールがあってもブロックが優先される。「ほぼ全部許可しつつ特定のコマンドだけ止めたい」場合は、`Bash`をallowに入れ、止めたいコマンドを`PreToolUse`フックで弾く構成が使える。

### 権限モード

| モード | 挙動 |
| --- | --- |
| `default` | 各ツールの初回使用時に確認(CLIでは「Manual」表記) |
| `acceptEdits` | 作業ディレクトリ内のファイル編集と`mkdir`・`touch`・`mv`・`cp`などを自動承認 |
| `plan` | 調査用の読み取りのみ。ソースの編集はしない |
| `auto` | 通常の確認なしで進み、バックグラウンドの分類器がユーザーの依頼に沿った操作かを確認する |
| `dontAsk` | 確認が必要になる操作をすべて**自動で拒否**する。事前にallowされたツールは動く |
| `bypassPermissions` | 確認をすべて省略する。コンテナやVMなど隔離環境でのみ使う |

- 起動時のモードは設定の`defaultMode`で決める。
- **CIなどの非対話実行**で止まらせたくない場合、`dontAsk`+必要なツールだけのallowリストなら、許可外の操作は確認待ちで止まらず拒否される。`bypassPermissions`を共有ランナーで使うのは危険。

### サブエージェントの定義

- **定義ファイル**はMarkdown+YAMLのfrontmatter。必須は`name`と`description`で、本文がシステムプロンプトになる。
- **場所と優先度**(高い順): managed設定 → `--agents`フラグ(セッションのみ) → `.claude/agents/`(プロジェクト) → `~/.claude/agents/`(ユーザー) → プラグインの`agents/`。チームで共有するものは`.claude/agents/`に置いてコミットする。
- **主なフィールド**: `tools`(許可ツール。省略すると継承)、`disallowedTools`、`model`、`permissionMode`、`maxTurns`、`skills`、`mcpServers`、`hooks`、`isolation: worktree`(一時的なgit worktreeに隔離)。
- **コンテキストの分離**: 各サブエージェントは独立したコンテキストウィンドウで動き、メインの会話に戻るのは最終的な要約だけ。
- **組み込み**: `Explore`(読み取り専用の高速検索)、`Plan`(プランモード用の読み取り専用調査)、`general-purpose`(探索と変更の両方)。
- **並列実行と入れ子**: 同時実行数の上限はデフォルト20。サブエージェントが別のサブエージェントを起動することもでき、デフォルトで最大3階層。ただし大量の結果を返すサブエージェントを多数走らせると、メインのコンテキストを圧迫する。

## 押さえておくべきポイント

- CLAUDE.mdは、ユーザー(個人のみ)・プロジェクト(共有)・ディレクトリの3階層。チームに配る規約はプロジェクトレベルに置く。`@import`と`.claude/rules/`でモジュール化する
- コマンドは`.claude/commands/`(共有)と`~/.claude/commands/`(個人)。スキルは`context: fork`・`allowed-tools`・`argument-hint`をフロントマターで設定する
- 散らばるファイルへの規約は、`paths`にglobを書いたパス指定ルールで条件付きに読み込む
- 大規模・複数案・アーキテクチャの判断はプランモード、範囲が明確な小さな変更は直接実行
- 説明が伝わらないときは入出力の具体例、テスト駆動、インタビューパターン。互いに影響する問題はまとめて、独立した問題は順番に
- CIは`-p`で非対話に、`--output-format json`+`--json-schema`で構造化。生成したセッションとは別のインスタンスでレビューする
- 設定はユーザーレベル/プロジェクトレベルで階層化し、チーム共有すべきルールはプロジェクト設定(リポジトリにコミット)に置く
- フックは「モデルの判断に依存させず機械的に強制したいルール」の実装場所。危険操作のブロックや監査ログはフックの典型用途
- サブエージェントはコンテキスト汚染の防止とツール権限の局所化に使う。並列化はスループットとコストのトレードオフ
- 権限モードはリスクベースで段階設計し、CI等の非対話実行では自動承認範囲を事前に厳密化する
- プロジェクト単位のMCP構成は認証情報を分離し、最小権限の原則をチームガバナンスとして適用する
- 組織導入は個人利用→設定の標準化→チーム展開という段階的ロールアウトが現実的
- 終了コード2だけがブロッキングエラー。`exit 1`などは非ブロッキングで処理が続行される。`PostToolUse`はツール実行後なので止める用途には使えない
- 権限ルールはdeny→ask→allowの順に評価され、どのスコープでもdenyは他のレベルのallowで覆せない。managed settingsが最上位
- 非対話実行(CI)では、`dontAsk`+必要最小限のallowリストで、確認待ちの停止もバイパスの危険も避ける
