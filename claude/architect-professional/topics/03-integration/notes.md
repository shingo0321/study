# 03. Integration (出題比率 19%・最重要ドメイン)

## この分野が問うこと

Claudeを既存の企業システム・クラウド基盤・データ基盤・認証基盤にどう統合するかという、最も配点の大きいドメイン。API/SDKレベルの統合パターンだけでなく、エンタープライズ認証、クラウドプラットフォーム経由の提供形態、MCPによる組織規模のツール接続、データパイプラインとの連携まで幅広く問われる。

## API/SDK統合パターン

- **Messages API直呼び出し**: シンプルなリクエスト/レスポンス型の統合。自前でツールユースループ・ストリーミング処理・エラーハンドリングを実装する必要がある。
- **Agent SDK / Tool Runner等の高レベルSDK**: エージェントループ(ツール呼び出し→実行→結果返却の繰り返し)を自前実装せずに済む。カスタムツールの登録、フック、サブエージェント委譲などの機能を活用して開発速度を上げる。
- **ストリーミング(Server-Sent Events)**: ユーザー体感レイテンシを下げるために、トークン単位でレスポンスを逐次表示する設計。長い出力やチャットUIでは必須に近い。
- **同期 vs 非同期処理**: 長時間かかるエージェントタスクは、リクエスト即時応答ではなくジョブキュー+Webhook/ポーリングによる非同期パターンで設計し、HTTPタイムアウトの制約を回避する。
- **バッチAPI**: リアルタイム性が不要な大量処理(夜間バッチでの分類・要約など)はバッチ処理用のエンドポイント/割引を活用してコストを下げる。
- **冪等性・リトライキー**: 統合層でのリクエストIDによる重複排除は、ネットワーク層のリトライと組み合わせて必須。

## エンタープライズ認証・IAM

- **SSO(SAML/OIDC)**: 社内ユーザーがClaudeベースのアプリケーションにアクセスする際、既存のIdP(Identity Provider、例: Okta, Azure AD/Entra ID)と連携し、認証を一元化する。
- **APIキー管理**: APIキーはシークレット管理サービス(Vault、Secrets Manager等)で管理し、コードやリポジトリに直書きしない。キーのローテーション・失効プロセスを運用に組み込む。
- **RBAC(ロールベースアクセス制御)**: どのユーザー/チームがどのモデル・どのツール・どのデータソースにアクセスできるかを、アプリケーション層またはゲートウェイ層で制御する。
- **最小権限の原則**: エージェントに与えるツール権限(特にデータ書き込み・外部送信系)は、タスク遂行に必要な最小限に絞る。過剰な権限付与はセキュリティリスクであり、05章のガバナンスとも直結する。
- **監査ログとの統合**: 誰が・いつ・どのプロンプトで・どのツールを実行したかを、既存のSIEM/ログ基盤に連携させる。

## クラウドプラットフォーム経由の提供(Bedrock / Vertex AI)

- Claudeは Anthropic直接API に加え、**AWS Bedrock**・**Google Cloud Vertex AI** 経由でも利用可能。企業が既にAWS/GCPのガバナンス・課金・コンプライアンス体制を持つ場合、これらのプラットフォーム経由での導入がスムーズ。
- 選定検討事項: 既存クラウド契約・データレジデンシー要件・既存IAMとの統合しやすさ・リージョン提供状況・モデルの提供タイミング(直接APIの方が新モデルの提供が早い傾向がある点は考慮に入れる)。
- **マルチプロバイダ冗長化**: 直接APIとBedrock/Vertexを併用し、片方に障害が出てももう片方にフェイルオーバーする設計は、01章の信頼性設計とも関連する重要パターン。
- プラットフォームごとにAPIの細かな形式(認証方式、レート制限の単位、対応リージョン)が異なるため、統合層で差異を吸収する抽象化レイヤーを設けると移行・併用が容易になる。

## MCP(Model Context Protocol)の組織規模での統合

- MCPは、LLMアプリケーションと外部データソース/ツールを標準化された方法で接続するオープンプロトコル。組織内で複数のツール(社内DB、チケット管理、ドキュメントストアなど)を個別に統合コードを書かずに接続できる利点がある。
- **組織規模でのMCPサーバー管理**: 各チームが個別にMCPサーバーを乱立させると、認証・監査・バージョン管理が分散し統制が効かなくなる。中央でMCPサーバーのレジストリ/カタログを持ち、承認済みサーバーのみを利用可能にするガバナンスモデルが望ましい。
- **セキュリティ考慮**: MCPサーバーは外部ツール実行の窓口になるため、認証(誰がどのMCPサーバーを呼べるか)・入力サニタイズ・ツールの権限スコープ制御が重要。信頼できないMCPサーバーの接続はサプライチェーンリスクになり得る(05章の指示注入・サプライチェーンリスクと関連)。
- **ローカル(stdio)vs リモート(HTTP/SSE)MCPサーバー**: ローカル実行は開発者個人環境向け、リモートは組織全体で共有するツール向け。本番の組織規模統合ではリモートMCPサーバーを中央でホスティングし、アクセス制御・可観測性を持たせる構成が現実的。
- MCPサーバーもソフトウェア資産として、バージョン管理・テスト・デプロイパイプラインの対象にする。

## データパイプライン統合

- **RAG基盤との統合**: ベクトルDB・検索エンジン(社内ドキュメント、ナレッジベース)とのインデックス更新パイプラインを設計し、鮮度(staleness)の許容範囲を定義する。
- **ETL/ストリーミング連携**: Claudeの出力を下流システム(DWH、BI、CRM)に流し込む場合、スキーマの安定性(構造化出力の契約化)が重要。LLM出力は柔軟だが、下流システムは厳格なスキーマを要求することが多いため、その間に検証層(バリデーション、リトライ、ヒューマンレビューのフォールバック)を挟む。
- **イベント駆動アーキテクチャ**: Webhookやメッセージキュー(Kafka, SQS等)をトリガーにエージェントを起動する構成は、既存業務システムとの疎結合な統合に向く。
- **レガシーシステムとの統合**: 古いSOAP API・オンプレミスDBなど、モダンなREST/JSON前提でないシステムとの接続には、アダプター層を設けてClaude側とのインターフェースを標準化する。

## 公式ブループリントの目標(試験ガイドv1.0)

> **出典**: 公式の試験ガイド(Claude Certified Architect – Professional、バージョン1.0、2026年7月施行)の、この分野の目標に沿った補足。

- **ツールやエージェントの構成と「機能の肥大」**: ツールやエージェントを増やしすぎると、選択精度が下がり、コストと保守の負担が増える。役割ごとに必要なツールだけを渡し、不要なものは外す。
- **認証と認可のギャップ**: エージェントが誰の権限で動くか(ユーザーの権限か、サービスの権限か)を明確にし、権限が過大になっていないかを点検する。最小権限と、操作ごとの認可確認が基本。
- **精度とレイテンシのトレードオフ**: 精度を上げる手段(大きなモデル、検索の追加、検証パス)は遅延とコストを増やす。構成の決定には、要件に基づく根拠を示す。
- **オブザーバビリティ**: 大規模環境では、リクエストごとのトレース、トークン数・遅延・エラー率・コスト、ツール呼び出しの成否を記録し、ダッシュボードとアラートで監視する。
- **RAGパイプライン**: 文書を分割(チャンキング)し、インデックスを作り、検索結果をコンテキストに渡す。
  - チャンキング: 小さすぎると文脈が失われ、大きすぎると無関係な内容が混ざる。見出しや段落など意味の区切りで分け、前後に重なりを持たせる戦略がある。メタデータ(出典、日付、種別)を付けておく。
  - インデックス: 埋め込み(ベクトル)による意味検索、キーワード検索、メタデータによる絞り込みを、データに合わせて組み合わせる。
- **検索戦略はデータの形状とクエリのパターンに合わせる**: 型番・ID・固有名詞の完全一致にはキーワード検索、言い換えを含む自然文の質問にはベクトル検索、両方が必要ならハイブリッド。構造化データには、SQLなどの構造化クエリ。
- **接続プロトコルの選択**: 再利用・共有したいツールや文脈にはMCP、既存のAPIやCLIで足りるならそれを直接使う、エージェント同士の連携にはエージェント間の仕組み。
- **段階的ディスカバリーと一括型コンテキスト**: 必要になったときに検索・読み込みして段階的に文脈を増やす方式は、コンテキストを節約でき、規模の大きいデータに向く。最初に全部を入れる一括方式は、単純で検索漏れがないが、コストが大きく、規模に限界がある。

## 押さえておくべきポイント

- 直接API・Bedrock・Vertex AIそれぞれの特性(データレジデンシー、既存IAM統合、モデル提供タイミング)を比較し、マルチプロバイダ冗長化の判断ができる
- SSO/RBAC/最小権限原則など、エンタープライズ認証・IAMの基本パターンをエージェントのツール権限設計に適用できる
- MCPは組織規模で使う際にレジストリ管理・認証・権限スコープなどのガバナンスが必要になる(乱立はリスク)ことを理解している
- LLM出力と下流システムのスキーマ不整合に備え、検証層・フォールバックを統合設計に組み込む発想を持つ
- 同期/非同期・ストリーミング/バッチなど、レイテンシ要件に応じた統合パターンの使い分けができる
