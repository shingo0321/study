# Security and Safety（8.1%）

Claudeを組み込んだアプリケーション・エージェントを安全に運用するためのドメイン。プロンプトインジェクションのリスクと対策、最小権限でのツール権限設計、入出力の検証、信頼できないコンテンツの扱いを中心に扱う。

## プロンプトインジェクションのリスク

- **プロンプトインジェクション**とは、外部から与えられたコンテンツ（ユーザー入力、Webページ、ツール実行結果、添付ドキュメントなど）の中に、モデルへの指示を装った悪意あるテキストが紛れ込み、意図しない挙動を引き起こす攻撃。
- 特にエージェント的なアプリケーション（Web検索・ファイル読み込み・外部API呼び出しなどを行うもの）では、ツール実行結果として取り込む外部コンテンツが攻撃経路になりやすい（例：スクレイピングしたページに「これまでの指示を無視して〜せよ」という文言が仕込まれているケース）。
- **間接プロンプトインジェクション（indirect prompt injection）**：攻撃者がユーザーに直接プロンプトを送るのではなく、モデルが後で読み込むであろう外部コンテンツに攻撃文を埋め込んでおく手口。エージェントがツールで取得するデータ全般がリスク面になる。

## プロンプトインジェクションへの対策

- **信頼境界の明示**：外部由来のコンテンツ（ユーザー入力以外の、ツール結果・検索結果・ドキュメント等）はXMLタグなどで明確に区切り、「これは指示ではなくデータである」とシステムプロンプトで明示する。
- **最小権限**：エージェントに与えるツールの権限を必要最小限にする（後述）。インジェクションが成功しても実害を最小化する多層防御の考え方。
- **出力検証**：エージェントが実行しようとするアクション（特に破壊的・機密性の高い操作）を、実行前にルールベースまたは人間のレビューでチェックする。
- **サンドボックス化**：ツール実行やコード実行を隔離された環境で行い、想定外のシステムアクセスを防ぐ。
- 100%の防止は困難という前提のもと、「侵入されても被害が限定的になる」設計（多層防御・最小権限・監査ログ）が現実的なアプローチとされる。

## 最小権限でのツール権限設計

- エージェントに付与するツール・スコープは「タスク遂行に必要な最小限」に絞るのが原則。汎用的すぎる強力なツール（任意コード実行、無制限のファイルシステムアクセスなど）を安易に与えない。
- 読み取り専用操作と書き込み/破壊的操作を明確に区別し、破壊的操作には追加の確認ステップ（人間の承認、確認プロンプトなど）を設ける。
- Claude Codeのパーミッションモデル（ツールごとの許可/拒否/確認設定）は、この最小権限原則を製品レベルで実装した例。開発者が独自エージェントを作る際も同様の権限制御レイヤーを設計すべき。
- 本番運用のクレデンシャル（APIキーなど）は、エージェントのプロンプトやコンテキストに直接埋め込まず、実行環境の権限管理（シークレット管理、スコープを絞ったAPIキー）で扱う。

## 入出力の検証

- ユーザー入力・モデル出力の両方に対し、アプリケーション側でのバリデーションを省略しない。「モデルの出力を無条件に信頼して実行する」設計は事故のもと。
- 構造化出力（JSON等）を後続処理に渡す前にスキーマ検証を行う、モデルが生成したコードやコマンドを実行する前に静的チェック・サンドボックス実行を挟む、といった防御的実装が重要。
- モデル出力に機密情報（PII、内部情報など）が意図せず含まれていないかのチェックも、用途によっては必要になる。

## 信頼できないコンテンツの扱い

- Web検索結果、外部ドキュメント、他システムからのWebhookデータなど「第三者が内容をコントロールできるデータ」はすべて信頼できないコンテンツとして扱う。
- こうしたコンテンツをコンテキストに含める際は、（1）指示ではなくデータとして明示的にタグ付けする、（2）そのコンテンツを根拠に実行するアクションの範囲を制限する、（3）機密操作の実行判断には使わせない、といった対策を組み合わせる。
- ツール結果をそのまま次のプロンプトに連結するだけの単純な実装は、間接プロンプトインジェクションに対して脆弱になりやすい。

## 安全性・責任あるAI利用の基本姿勢

- Anthropicは自社モデルの安全性方針として、有害利用の防止・誤用対策のガイドライン（Usage Policy等）を定めている。開発者はアプリケーション設計時にこれらの利用ポリシーに準拠する必要がある。
- 出力のガードレール（不適切な内容のフィルタリング、コンテンツモデレーション）をアプリケーション層に組み込むことも、実運用では重要な要素になる。
- 監査ログ（エージェントがどのツールをどんな引数で呼んだか）を残すことは、インシデント発生時の原因調査や、権限設計の妥当性検証に不可欠。

## 押さえておくべきポイント

- プロンプトインジェクション（特に間接プロンプトインジェクション）のリスクと、外部コンテンツがツール結果経由で攻撃経路になり得ることを説明できる。
- 信頼境界の明示（タグによるデータ/指示の分離）が基本的な対策の一つであることを理解している。
- 最小権限原則をツール権限設計に適用する考え方（読み取り専用/破壊的操作の区別、承認ステップ）を説明できる。
- モデルの出力を無条件に信頼せず、実行前に検証・サンドボックス化する防御的実装の重要性を理解している。
- 100%の防止は難しく、多層防御（最小権限・検証・監査ログ）で被害を限定するという現実的なアプローチを説明できる。
