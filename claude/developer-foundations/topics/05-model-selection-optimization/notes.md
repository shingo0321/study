# Model Selection and Optimization（16.8%）

用途に応じて適切なClaudeモデルを選び、コスト・レイテンシ・品質のバランスを最適化するためのドメイン。モデルファミリーの特性、拡張思考（extended thinking）、コンテキストウィンドウ管理、プロンプトキャッシュによるコスト最適化などを扱う。

## モデルファミリー（Haiku / Sonnet / Opus）

- Claudeのモデルは大きく3系統：**Haiku**（最速・最安、軽量タスク向け）、**Sonnet**（速度と知能のバランス、多くの実運用ワークロードの既定選択）、**Opus**（最も高い知能、複雑な推論・高難度タスク向け、コスト・レイテンシは最大）。
- 一般的なトレードオフ：知能が高くなるほどコスト（トークン単価）とレイテンシ（応答までの時間）が増える。すべてのタスクに最上位モデルを使うのはコスト効率が悪い。
- 選定の考え方：
  - 分類・抽出・簡単な要約・定型応答・大量バッチ処理 → Haiku
  - 一般的なチャット、コーディング支援、中程度の推論を要するエージェントタスク → Sonnet
  - 複雑な多段階推論、高精度が要求される専門的タスク、難易度の高いコーディング → Opus
- 実運用では「まず軽量モデルで試し、精度が不足する場合にのみ上位モデルへ」という段階的アプローチや、タスクの難易度によって動的にモデルを切り替える設計（ルーティング）も選択肢になる。

## コスト最適化の基本戦略

- **モデル選定**：タスクの複雑さに対して過剰なモデルを使わない。
- **プロンプトキャッシュ**：固定プレフィックス（システムプロンプト、ツール定義、長い参照ドキュメント）を使い回すことでinputトークンのコストを削減。
- **出力トークンの制御**：`max_tokens` の適切な設定、不要な冗長出力を避けるプロンプト設計（出力トークンは入力トークンよりも一般に単価が高い）。
- **バッチ処理**：即時応答が不要なワークロードには、非同期でまとめて処理する仕組み（バッチAPI）を使うことでコストを抑えられる場合がある。
- **プロンプトの簡潔化**：冗長な指示やコンテキストを削り、本当に必要な情報だけを渡す。

## 拡張思考（Extended Thinking）

- 一部のモデルでは、回答を出す前にモデル内部で「思考過程」を長く展開させる**拡張思考モード**を利用できる。複雑な数学・論理推論・多段階の計画立案などで精度向上に寄与する。
- 拡張思考には追加のトークン消費（＝コストとレイテンシの増加）が伴うため、常時オンにするのではなく、タスクの難易度に応じて使い分けるべき機能。
- 単純なタスク（分類、簡単なQ&A、フォーマット変換など）では拡張思考のメリットは小さく、コストだけが増える。
- 出力の一部として「思考の中身」が返る場合、それをそのままエンドユーザーに見せるべきかどうかはアプリケーション設計上の判断事項（内部推論であり最終回答そのものではない）。

## コンテキストウィンドウ管理

- モデルには入力として扱えるトークン数の上限（コンテキストウィンドウ）がある。長い会話・大量のドキュメント・多数のツール定義を積み重ねると上限に近づく。
- コンテキストが大きくなるほど、レイテンシとコストが増加し、また関連情報が埋もれて精度が落ちる（"lost in the middle" 的な現象）リスクもある。
- 管理戦略の例：
  - 古い会話履歴の要約・圧縮（サマリー化してから継続）
  - 不要になったツール結果・中間生成物の切り捨て
  - RAG（検索拡張生成）的に、必要な情報だけを都度取得してコンテキストに注入する
  - 長期記憶が必要な場合は外部ストレージ（ファイル、DB、ベクトルDBなど）に退避し、必要な時だけ読み込む
- エージェントのマルチターンループでは、ターンを重ねるごとにコンテキストが線形に増えていくため、定期的な要約・剪定の仕組みを組み込むのが一般的。

## レイテンシ最適化

- ストリーミングを使うことで「体感レイテンシ」（最初の応答が出るまでの時間）を改善できる（実際の総生成時間が短縮されるわけではない点に注意）。
- 出力トークン数を絞る（不要な説明を省く指示、`max_tokens`の適切な設定）ことで生成時間自体を短縮できる。
- 並列化できるタスク（独立した複数の呼び出し）は逐次実行せず並行実行することでスループットを改善できる。
- モデルサイズ・拡張思考の有無もレイテンシに直結するため、リアルタイム性が求められるユースケースほど軽量モデル・拡張思考オフが基本線になる。

## モデル移行・バージョニング

- Claudeのモデルは定期的に新バージョンがリリースされる。本番アプリケーションでは、特定バージョンに固定するか、最新版へ自動追従するかを運用方針として決める必要がある。
- バージョンアップ時は出力の傾向（トーン、フォーマット遵守など）が変わり得るため、移行前に評価（eval）で回帰がないか確認するプロセスが推奨される。

## 押さえておくべきポイント

- Haiku/Sonnet/Opusの特性（コスト・速度・知能のトレードオフ）と、タスク難易度に応じた選定基準を説明できる。
- コスト最適化の主要手段（モデル選定、プロンプトキャッシュ、出力トークン制御、バッチ処理）を挙げられる。
- 拡張思考は精度向上とコスト/レイテンシ増加のトレードオフであり、タスクに応じて使い分けるべきものと理解している。
- コンテキストウィンドウが有限であることによるリスク（コスト増、精度低下）と、その管理手法（要約、剪定、RAG的な注入）を説明できる。
- レイテンシ改善の手段としてストリーミング・出力トークン抑制・並列実行・軽量モデル選択を挙げられる。
- 本番運用ではモデルバージョンの移行方針と、移行前の評価プロセスが重要であると理解している。
