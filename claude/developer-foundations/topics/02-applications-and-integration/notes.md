# Applications and Integration（33.1%）

試験範囲の中で最も比重が大きいドメイン。Claude API（Messages API）を使ったアプリケーション構築の基礎知識全般——リクエスト/レスポンスの基本構造、ストリーミング、ツールユース（function calling）、プロンプトキャッシュ、エラーハンドリング、SDK利用、構造化出力、Claude Agent SDKによるカスタムエージェント構築までを含む。実務でAPIを組み込む開発者が最も差がつく領域。

## Messages API の基本

- Claudeとの対話は **Messages API**（`/v1/messages`）が中心。会話は `messages` 配列（`role: "user"` / `"assistant"` の交互）として渡す。
- リクエストには `model`（使用するモデルID）、`max_tokens`（生成する最大トークン数の上限）、`messages` が最低限必要。
- `system` パラメータでシステムプロンプト（役割・制約・出力形式などの指示）を独立して渡せる。会話履歴の`messages`とは別枠。
- レスポンスには生成テキストの他に `stop_reason`（`end_turn`, `max_tokens`, `stop_sequence`, `tool_use` など、なぜ生成が終わったか）や `usage`（入力/出力トークン数）が含まれる。
- Claudeは基本的に**ステートレス**なAPI。会話の継続は毎回全履歴をクライアント側で組み立てて送る必要がある（サーバー側にセッションは保持されない）。

## ストリーミング

- `stream` を有効にすると、レスポンスをトークン単位/イベント単位で逐次受信できる（Server-Sent Events, SSE）。
- ユーザー体験の改善（生成中でも表示を始められる）や、長い出力でのタイムアウト回避に有効。
- イベントには開始・テキスト差分・ツール呼び出しの差分・終了などの種類があり、クライアント側でイベントの種類ごとに処理を組み立てる必要がある。
- 非ストリーミングでは大きな出力がタイムアウトしやすいため、長文生成やエージェント処理では基本的にストリーミングが推奨される。

## ツールユース（Function Calling）

- Claudeに外部関数・APIを「呼び出す能力」を持たせる仕組み。開発者がツールの名前・説明・入力スキーマ（JSON Schemaベース）を定義してリクエストに含める。
- Claudeはユーザーの要求に応じて、自らテキストを生成する代わりに「このツールをこの引数で呼びたい」という `tool_use` を返す。実際の実行はクライアント（開発者側のコード）が行い、結果を `tool_result` として会話履歴に追加して次のリクエストを送る、というループになる。
- ツールの `description`（何をするツールか、いつ使うべきか）を明確に書くことが呼び出し精度に直結する。曖昧な説明や似た名前のツールの乱立は誤呼び出しの原因になる。
- 複数ツールを並行して呼び出す（parallel tool use）ことも可能。逐次実行が必須の場合は、その旨をプロンプトやツール設計で明示する必要がある。
- **構造化出力**の手段としてもツールユースは有効：「1つのツールだけを強制的に呼ばせる」ことで、JSON Schemaに沿った構造化データを確実に取得できる（自由文出力よりパースが安定する）。

## プロンプトキャッシュ（Prompt Caching）

- 長いシステムプロンプト・大量のツール定義・長いドキュメントなど、リクエストの前半部分（プレフィックス）が変わらない場合、その部分をキャッシュしてコスト・レイテンシを削減できる仕組み。
- キャッシュ対象は「キャッシュブレークポイント」で明示的にマークする。キャッシュのヒット時は該当部分の処理コストが大幅に下がる（通常のinputトークンより安価）。
- 効果が出やすいのは：同じシステムプロンプト/ツール定義で多数のリクエストを送るケース、長いコンテキスト（ドキュメント、few-shot例）を使い回すケース、マルチターンのエージェントループ（毎ターン同じ履歴プレフィックスを送る）。
- キャッシュには有効期限があり、一定時間アクセスがないと失効する。頻繁にアクセスされる想定でないプレフィックスにはメリットが薄い。

## エラーハンドリングとレート制限

- APIはHTTPステータスコードでエラー種別を返す（クライアント側の入力ミス、認証エラー、レート制限超過、サーバー側の一時的エラーなど、大きく「リトライすべきでないエラー」と「リトライすべきエラー」に分かれる）。
- レート制限は主にRPM（requests per minute）とTPM（tokens per minute）の両面で管理されており、超過時はレート制限エラーが返る。
- レート制限やサーバー一時エラーへの対処は**指数バックオフ（exponential backoff）付きのリトライ**が基本パターン。SDKには自動リトライ機能が組み込まれていることが多い。
- 本番運用では、モデルの過負荷やタイムアウトに備えたフォールバック設計（別モデルへの切り替え、キューイングなど）も検討課題になる。

## SDK（Python / TypeScript）

- Anthropic公式SDKがPython・TypeScript（JavaScript）向けに提供されている。生のHTTPリクエストを書かずに、型安全にMessages APIを呼べる。
- SDKはリトライ・タイムアウト・ストリーミングのハンドリングなど、上記のような定型処理を吸収してくれる。
- 環境変数（APIキー）によるクライアント初期化が一般的で、キーをコードにハードコードしないことがベストプラクティス。

## Claude Agent SDK

- 単発のAPI呼び出しではなく、「計画→実行→観察」を繰り返す**エージェント的なアプリケーション**を構築するためのSDK（旧Claude Code SDKから発展したもの）。
- ツール実行・ファイルアクセス・サブエージェントの起動・パーミッション制御・コンテキスト管理など、エージェントループに必要な部品をあらかじめ提供する。
- Claude Code自体もこのSDKの上に構築されている、という位置づけ。カスタムのコーディングエージェントや業務自動化エージェントを自前で作りたい場合の土台になる。
- 独自ツールの登録、MCPサーバーとの接続、システムプロンプトのカスタマイズなど、アプリケーション側の要件に合わせて拡張できる設計になっている。

## 構造化出力

- Claudeに厳密なJSON/スキーマ準拠の出力をさせたい場合、（1）プロンプトで出力形式を明示する、（2）ツールユースを使い「1つのツールを強制的に呼ばせる」ことでスキーマに沿ったデータを取得する、という2つの主なアプローチがある。
- 特にダウンストリームのシステム（DB書き込み、他APIへの連携など）に渡す場合は、パースの信頼性からツールユース方式が好まれることが多い。
- 出力形式の逸脱を減らすには、スキーマの各フィールドに明確な説明を与える、例を1つ以上示す（few-shot）、といった工夫が有効。

## 押さえておくべきポイント

- Messages APIはステートレス。会話継続は毎回全履歴を送る設計であることを理解している。
- ストリーミングが必要になる典型シナリオ（長文生成、UX改善、タイムアウト回避）を説明できる。
- ツールユースの一連の流れ（ツール定義→`tool_use`→クライアント実行→`tool_result`→次のリクエスト）を順序立てて説明できる。
- プロンプトキャッシュが効くパターン（固定プレフィックスの再利用）と効かないパターンを区別できる。
- レート制限・一時エラーへの基本対処が指数バックオフ付きリトライであることを知っている。
- 構造化出力を安定して得るために、ツールユースを応用できることを理解している。
- Claude Agent SDKが「単発API呼び出し」と「エージェント的アプリケーション構築」の間のギャップを埋める位置づけであることを説明できる。
